# Merging Duplicate PRR Risks & OneDrive Snapshot Stub Pitfall

## When to merge (de-dup candidates to look for)

Duplicate PRR risks appear when the same underlying threat is tracked under
two IDs — typically one from the original PM register and one created later by
the document-intake pipeline. Patterns seen on Aseer:

| Group | Survivor | Merged-away | Rationale |
|-------|----------|-------------|-----------|
| EOT/time dispute | `PRR-COM-01` | `PRR-COM-05` | Same EOT claim (LT-0007 + earlier rejected Claim 01) |
| Open NCRs | `PRR-STK-02` | `PRR-NCR-001` | Exact-duplicate NCR tally (13/4/3/6), one created by `document_intake.py` |
| Remote logistics/materials | `PRR-LOG-01` | `PRR-LOG-02` + `PRR-CON-05` | Same oversized deliveries + remote material shortage |

**Precedent:** prior merge `47f18ca` (4 dup risks → 51) used the same pattern.

## Merge workflow (proven 2026-08-18)

1. **List risks** from `06_Risk_System/risks.json` (SoT). Identify dup groups by shared cause/evidence/owner.
2. **Read full fields** of each candidate first (cause/event/consequence/response_action/actions/history/evidence) — never merge on title alone.
3. **Edit the SoT `risks.json`** with a script:
   - Remove merged-away IDs from the `risks` array.
   - Absorb evidence (dedupe), actions (prefix text `[absorbed from <ID>] `), and history into the survivor.
   - Set survivor `last_reviewed` = today, append a `[MERGE YYYY-MM-DD: ...]` note to `response_action`.
   - Refresh `total_risks` / `total` fields.
4. **Propagate to every mirror**, not just `risks.json`:
   - `prr_risks.json` (full mirror)
   - `dashboards/risks.json` — **curated subset** (only ~35 of 73); it may LACK some survivors (e.g. no `PRR-LOG-01`, `PRR-NCR-001`). Handle separately: just drop the merged-away IDs that are present, don't try to resolve absent survivors.
   - `01_Registers/risk_register.md` — regenerate via `python3 risk_sync.py --json risks.json` (auto-generated, do not hand-edit).
   - Treatment files `03_Plans/08_Risk/treatment/`: rewrite merged-away file to `status: merged` + `merged_into:` frontmatter (keep it, don't delete); append a `## Merge (date)` note to survivor files.
   - `scripts/document_intake.py` — update the keyword→risk_id `risk_map` (e.g. `"ncr": "PRR-STK-02"`) so future intake writes to the survivor.
   - **Do NOT touch** `risk_breakdown_structure.md` category entries — `COM-05`/`CON-05`/`LOG-02` there are RBS *category codes*, not risk IDs; leave them if the category still has other risks.
5. **Rebuild + deploy** from `06_Risk_System/webapp/`: `python3 build_snapshots.py --bump`, then `bash deploy.sh`.
6. **Verify live**: parse `const RISK = {...}` from the served HTML; assert count dropped and merged-away IDs absent. Note LiteSpeed cache — append `?cb=...` query param and check again after post-commit hook runs.
7. **Commit with YYYY-MM-DD** in the message (user requires dates in every commit).

## Pitfall: OneDrive submission-snapshot stubs (Excel "file format not valid")

The RMP `05_Submittle/REV01/` subfolders hold **submission snapshots** named
`Aseer_Museum_{PRR|DDR|HSE|AVR}_Snapshot_YYYY-MM-DD.xlsx`. If OneDrive
files-on-demand never fully downloaded them, the file is a **4,511-byte HTML
stub** containing `<title>This Page Does Not Exist</title>` — NOT a real xlsx.
Excel refuses to open it with "file format or file extension is not valid".

**Detection:**
```bash
file "Aseer_Museum_PRR_Snapshot_2026-08-16.xlsx"
# -> "HTML document text, ASCII text"  (bad)  vs  "Microsoft Excel 2007+" (good)
```
Real files are 160–205KB; stubs are ~4.5KB. All four snapshots were stubs at once.

**Fix:** regenerate from the repo's built snapshots and copy in:
```bash
BASE=".../04_Registers/05_Submittle/REV01"
# PRR
cp 06_Risk_System/webapp/src/EXP-RISK-PRR-2026-038_RevC20_ACTIVE.xlsx \
   "$BASE/01_Master_Risk_Register/Aseer_Museum_PRR_Snapshot_2026-08-18.xlsx"
# DDR -> 02_Design_Risk_Register ; HSE -> 03_HSE_Risk_Register ; AV -> 04_AV_Risk_Register
```
Use the newest `EXP-RISK-*_ACTIVE.xlsx` from `webapp/src/` (PRR/DDR/HSE) and
`webapp/av/src/` (AVR). Move corrupt stubs to `_CORRUPT_<date>/` rather than
deleting (OneDrive-safe; never delete without explicit confirmation).

**These OneDrive REV01 snapshots are NOT auto-synced from the repo** — they must be
regenerated by hand (or via automation) after every register change. Offer to set
up automation if the user wants it.
