# GitHub Issue Triage — Aseer Museum PM (sultandroid/aseer-museum-pm)

Applies when the user asks to "عالج الكل" (handle all) open issues, "شوف المشكله N" (look at issue N), or review the repo's open issues. The repo has ~200 open issues; most are auto-generated and must NOT be closed blindly.

## Step 1 — Classify by label before touching anything

```bash
gh issue list -R sultandroid/aseer-museum-pm --state open --limit 300 \
  --json number,title,labels -q '.[] | "\(.number)\t\([.labels[].name]|join(","))\t\(.title)"' \
  | awk -F'\t' '{print $2}' | sort | uniq -c | sort -rn
```

Two distinct populations:
- **`risk-tracker,risk-daily,<REG>`** (PRR/DDR/HSE/AV) — auto-generated by `scripts/risk_issue_daily.py` from `06_Risk_System/*_risks.json`. These mirror live risk state. **Do NOT close them manually** — the daily cron closes them when the risk status flips to Closed/Mitigated in the JSON.
- **Everything else** (question, known-issue, commercial, bug, discussion, documentation) — genuinely actionable.

## Step 2 — Risk-tracker issues: verify sync, don't close

```bash
cd ~/aseer-museum-pm && python3 scripts/risk_issue_daily.py --dry-run
```
If it reports `Unchanged=<N> MissingIssue=0 Errors=0`, all risk issues are in sync with the JSON source of truth — they are legitimately open. Closing them would be false. Report this to the user and move on.

## Step 3 — For actionable issues, verify CURRENT state before closing

An issue may already be closed, or the fix may already be applied by a sibling agent / earlier session. Check:
```bash
gh issue view <n> -R sultandroid/aseer-museum-pm --json state,comments
```
- **Already closed** → don't re-close; just add an evidence comment if useful.
- **Fix already in repo** → verify the actual file/script state (grep the register, read the script), then close with the evidence.
- **Genuinely pending external action** (awaiting Waris/Nader/Finance/HR/sign-off) → leave OPEN. Do not close falsely. Report what's blocking.

## Step 3.5 — Partial close: document what IS resolved, keep the issue open

When an issue's core question is answered but real work remains (contract not signed, price not agreed, NCR open), do NOT fully close and do NOT just leave it silent. Post a **"Partial close"** comment that:
1. States what IS resolved, with evidence (SOW done, specialist appointed, price under negotiation).
2. Lists what is STILL open (no signed contract, no construction quotation, NCR live, payment trace unresolved).
3. Explicitly says "Not closing fully — <reason>."

This keeps the issue visible for the outstanding action without falsely marking it done. Verified 2026-08-28: issue #44 (landscape quotations) — SOW finalized (MOC-MUS-ASE-1L0-ZD-0116 Rev.01) + TLC appointed + price under negotiation (SAR 120k→100k→130k), but no contract and no construction quotation → partial close, left open. The user explicitly asked for this: "ضيف هذا التعليق اغلاقها جزئيا في تفاوض علي عرض سعر لكن لسه مفيش تعاقد" (add this comment, close it partially — price under negotiation but no contract yet).

## Step 4 — Close with evidence, not a bare close

Always `gh issue close <n> --comment "..."` with:
- The verified fix (file path + commit hash, or the actual current state).
- The evidence source (Outlook email IDs, register rows, doc refs, CG codes).
- Any remaining action item, clearly separated.

## Step 5 — Git push discipline (this repo)

The repo has a post-commit hook that regenerates `06_Risk_System/webapp/src/index.html` (dirtying the tree) and sibling agents edit registers concurrently. When pushing:
1. `git add <your files> && git commit -m "..."`.
2. If push rejected (remote ahead): `git stash push -m "wip"`, `git pull --rebase origin main`, `git push origin main`, `git stash pop`.
3. On rebase conflict in a register you edited: the remote (sibling) version may already contain the fix — `git checkout --theirs <file>` and drop your redundant change rather than forcing yours.
4. Verify the push landed (`git log --oneline -1` / push output) before telling the user it's on the repo.

## Pitfalls
- **Sibling agents edit the same registers** — a `patch` may return `_warning: modified by sibling subagent`. Re-read before writing; prefer the remote version when it already has the fix.
- **`gh issue view` with `-q` jq expressions can fail** on multi-line bodies — use `--json` + a Python one-liner instead.
- **Don't re-open a risk** just because Code B carried comments (AGENTS.md Rule 10: Code B = practical final approval, risk closed).
