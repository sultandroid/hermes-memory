# Multi-Source Risk Register Update

## The Problem

The risk register lives in 4+ places. Changing a single risk (owner, status, date, score) requires updating ALL of them. Missing one creates inconsistency that the user will catch.

## Update Sequence (one risk changed)

```
1. Edit 02_Registers/risk_register.md row         (patch tool — keep response_action, target date, evidence in sync)
2. Edit 12_WeBsite/Risk/risks.json entry           (patch tool — keep P/S/score/rating/owner/target_close/actions/history/response_action in sync)
3. If no treatment file exists yet, write 04_Plans/08_Risk/treatment/PRR-XX-XX.md (see "Adding a new action to an existing risk" below)
4. If treatment file exists, patch it (update action statuses, add new actions, refresh last_updated frontmatter)
5. Rebuild webapp:  cd 12_WeBsite/Risk && python3 build_risk.py   (regenerates index.html + xlsx)
6. Deploy:  bash ~/Desktop/deploy.sh
```

Steps 1–2 are the minimum for any single-field update. Step 3 is required the first time a risk gets mitigation actions — every non-trivial risk should have one (see "Treatment file rule" below). Steps 5–6 only matter if the live webapp should reflect the change.

## Adding a new action to an existing risk (the common case)

When the user gives a mitigation directive mid-review (e.g. "we mitigate by arranging a coordination meeting and linking NRS with ZNA"), the change touches multiple fields in `risks.json` plus the MD row plus the treatment file. Checklist:

1. **`risk_register.md` row** — update `response_action` column, `target close` column, `evidence` column. Keep all on one line.
2. **`risks.json` entry**:
   - `last_reviewed` → today's date
   - `target_close` → bumped to absorb the new action's due date (don't pretend the old target still works)
   - `treatment_file` → set to the path in #3 if it was null
   - `evidence` array → append a reference to the new MoM / submittal
   - `response_action` → updated to mention the new mechanism
   - `actions` array → append the new action with `id: "A{n}"`, `owner`, `due`, `status: "In Progress"`, `evidence: ""`
   - `history` array → append a `Reviewed` entry summarising the change and why
3. **Treatment file** — if creating, match the YAML frontmatter of `PRR-DES-01.md` exactly (`last_updated`, `owner_agent`, `status`, `risk_id`, `source`). Add the action table. For meeting-driven mitigations, draft the MoM inside the treatment file (see below).

The "Add a new action" example from 2026-07-25 (PRR-DES-04) is in `references/prr-action-addition-workflow.md`.

## Treatment file rule

Every risk in the live PRR with a `response_action` other than "Monitor" / "Watch" should have `treatment_file` populated in `risks.json` and a corresponding file at `04_Plans/08_Risk/treatment/PRR-XX-XX.md`. Treatment files are the formal record of:

- The risk statement and current score
- The response strategy (Mitigate / Avoid / Transfer / Accept / Active monitoring)
- The action table with owner, due, status, evidence
- The residual risk target
- For meeting-driven mitigations: the MoM draft (see "Meeting-as-mitigation" below)

Use `PRR-DES-01.md` as the canonical format template. Match its YAML frontmatter keys exactly so the deploy pipeline can index them. Naming: `PRR-{CAT}-{NN}.md` zero-padded (e.g. `PRR-DES-04.md`, not `PRR-DES-4.md`).

## Meeting-as-mitigation pattern

When the mitigation is "arrange a coordination meeting between [party A] and [party B]", don't create a separate MoM file. Draft the MoM agenda + attendees + outputs **inside the treatment file** under a `## Coordination meeting — MoM-NN draft` heading. Then:

- Use the MoM ID (e.g. `MoM-15`) as the `evidence` value in the new action and in the `risk_register.md` evidence column
- Reference the MoM in the `history` entry so the audit trail points to a concrete document
- Leave any contact not in memory as `TBC` and surface to the user — never fabricate email addresses

This keeps the meeting logistics with the risk that motivated it, so closing the risk and closing the MoM are the same review action.

## Risk Classification: Site vs Design

A risk that mentions "DD package" or "design" in its title may still be a **site-work risk** if the mitigation involves site investigations (core testing, rebar scanning, geotechnical boreholes, structural surveys).

**Canonical example — PRR-DES-07:**
- Title says "Structural DD 50% package returned Code C"
- But the mitigation is: core testing, rebar scan, geotechnical borehole — all site execution
- Owner should be **Construction Manager**, not Technical Office Manager

**Rule of thumb:** When in doubt, check whether the primary mitigation is:
- Site execution (core testing, surveys, installation, commissioning) → **Construction Manager**
- Document production (drawings, submittals, reports, specs) → **Technical Office Manager**
